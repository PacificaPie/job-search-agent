# 这套系统能不能 agent 化？能，但先别急着让 LLM 开循环

状态：v2（2026-08-28，补入 Campaign 决策层）
关联：`goal-一条龙系统蓝图.md` 第 1 节与 P6、`evals/README.md`

---

## 1. 先说结论

**能改，而且改造点很清楚；但直接上「LLM 自主循环」是这套系统当下最差的一步棋。**

理由不是保守，是这套系统的失败代价不对称：

- 抓错一个岗位，成本 = 人工审核台里多划一下；
- 发错一条招呼语给真招聘者，成本 = 不可撤回，而且伤害的是本人的求职信誉。

在这种代价结构下，「让 LLM 决定下一步做什么」的收益（省几分钟排程）远小于
「LLM 某次抽风把不该发的推到发送边界」的风险。所以正确顺序是：
**先把 agent 的骨架（工具层 + 决策层 + 可回归测评）搭出来，让确定性版本先跑，
再把决策权一格一格交给 LLM。** 每交一格，都得有测评证明它不比确定性版本差。

这也正好是 `evals/` 昨天先落地的原因——测评先行不是流程洁癖，是让「敢不敢交权」
这个问题有答案。

## 2. 现状诚实盘点：它是流水线，不是 agent

| Agent 要件 | 现状 | 差在哪 |
|---|---|---|
| 工具集 | capture / evaluate / draft / review / application 都已经是干净的服务方法 | 没有统一的 tool 描述（名字、参数、**副作用等级**），LLM 没法选 |
| 决策循环 | 无。`daily_cli` 写死顺序：抓 → 筛 → 生成 → 等人审 | 没有「今天该干什么」这一层 |
| 记忆 | SQLite 有事务记忆；archive.md 是静态经历库 | 没有**反馈记忆**：哪类岗位真的有回复，从来没有回流去改打分权重 |
| 人机边界 | ✅ 发送/提交全人工。这是这套系统最值钱的设计 | 保持，且要在**结构上**保持（见 §4） |
| 测评 | ✅ L0 Campaign 4/4、L1 20/20、L2 国内 7/7 + 海外 4/4 | L3 未接；决策层（L4）还不存在 |

一句话：**LLM 现在被当成两个纯函数在用（打分、写文案），没有任何选择权。**

## 3. 三个真正值得 agent 化的决策点

不是所有环节都值得。判据是「这里是否存在人每天都要重复做、且依赖当前状态的判断」。

**① 当日操盘（最值得做，已有单队列确定性版本）**
今天数据库里躺着 95 个岗位、44 个 needs_review、5 个 eligible、0 条投递，日限额 12。
今天应该：先清 needs_review 积压？还是去抓新岗位？还是先把 5 个 eligible 的草稿写了？
这是一个**依赖当前状态的排程决策**，人每天都要做一遍，且规则可以先写死、再交给 LLM。

下一版不能继续只看聚合的 `eligible` / `needs_review`。国内 BOSS 和海外 New Grad
需要不同后续动作，planner 应读取 `campaign_states`，先决定在哪条 Campaign 投入时间，
再决定该方向内是抓取、审核、准备材料还是跟进。

**② needs_review 的二次排序（次值得）**
44 条 needs_review 占了 46%，人工审核台会被灌满。现在它们是无序的一堆。
真正该做的是：对 needs_review 也跑 L2 打分，按分排序，让人先看最可能有价值的。
这不需要 LLM 做决策，只需要把已有的打分工具用在一个新位置上——**收益最高、风险最低**。

**③ 反馈回流（最有 agent 味，但必须等数据）**
applications 表刚建好（本次 P2）。等积累了几十条投递结果，就能回答：
「哪类岗位真的有回复」。把它回流去调打分权重/关键词，系统才第一次有了**演化的记忆**，
而不只是事务记忆。这是唯一能让「agent」这个词名副其实的部分，但**现在数据量是 0，
硬做就是自欺欺人**。

反过来，**不该 agent 化的**：浏览器操作（确定性代码更可靠，且 LLM 点错的代价是账号风控）、
招呼语校验（`validate_letter` 必须是硬规则，不能被"说服"）、发送决策（红线）。

## 4. 关键设计：红线要靠结构保证，不能靠提示词

给 LLM 的系统提示里写「不许发送」是**没有安全边界的**——提示词可以被 JD 正文里的
注入内容绕过（招聘 JD 是不可信输入！）。正确做法是：

> **工具箱里根本不存在「发送」这个工具。**

本次实现的 `agent/tools.py` 因此给每个工具打了副作用等级：

- `READ`：只读 DB，随便调；
- `WRITE_LOCAL`：只写本地 DB（生成草稿、开投递记录），可调但会留审计；
- `EXTERNAL`：任何对外产生不可撤回影响的动作 —— **注册表里一个都没有，且注册时会拒绝**。

这样即便未来的 LLM 决策层被 JD 里的 prompt injection 忽悠了，它能调到的最坏工具
也只是「在本地数据库里多写一条草稿」，而不是把消息发出去。

## 5. 路线（每步都能独立验收）

| 步 | 内容 | 验收 | 状态 |
|---|---|---|---|
| A1 | 工具层：统一 tool 描述 + 副作用等级，结构性禁止 EXTERNAL | 注册 EXTERNAL 工具会抛异常；只读工具不写库 | ✅ 本次 |
| A2 | 确定性操盘 planner：读 DB 状态 → 输出今日行动清单 | 给定状态产出可复现的清单；纯函数，无副作用 | ✅ 本次 |
| A3 | `reachout-plan` CLI：早上一条命令看今天该干什么 | 真库跑出来的清单和人工判断一致 | ✅ 本次 |
| A4 | Campaign 地基：岗位与求职方向多对多，分别保存召回与判断 | 两条 daily 链路写入各自 Campaign；旧流程兼容 | ✅ 本次 |
| A5 | Campaign 审核台：分方向展示并在各自范围内二次排序 | 不跨 Campaign 比较裸分；后续动作与渠道匹配 | 待做 |
| A6 | Campaign-aware 确定性 planner + L4 测评 | 构造多 Campaign 状态快照，确定性版本作为基线 | 待做 |
| A7 | LLM planner：同样的状态喂给 LLM，让它选工具、给清单 | **必须在 L4 上不劣于确定性基线**，否则不上线 | 待做 |
| A8 | 反馈回流：从 applications 算各 Campaign 回复率 → 调整投入与权重 | 变化可解释；改前后跑 L1/L2 回归 | 等数据 |

**A7 的验收标准是这份方案里最重要的一句话**：LLM 决策层不是"做出来就用"，
而是要先在测评上打赢那个几十行 if-else 写成的确定性 planner。打不赢就说明
这个环节根本不需要 LLM——这也是一个有价值的结论，而不是失败。

## 6. 怎么对外讲这个项目

不要说「我做了一个求职 agent」——面试官追问决策循环就穿帮了。

准确的说法是：**「human-in-the-loop 的求职系统，确定性工具层 + 可回归测评先行，
决策层正在按测评结果逐步交给 LLM」**。这个叙事的强度不在于用了多少 LLM，
而在于**能说清哪里不该用 LLM、以及凭什么这么判断**——这恰恰是 AI 产品经理
比"会调 API"更稀缺的能力。
